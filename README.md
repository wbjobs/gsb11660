# Web Locks 多标签页锁竞争演示

纯前端、零构建的演示应用：在多个浏览器标签页之间竞争同一把锁，实时可视化临界区、
锁等待、超时降级、锁释放、死锁避免与崩溃自动回收。

## 运行

```bash
cd B
python3 -m http.server 8080
# 打开 http://localhost:8080 ，并多开几个标签页访问同一地址
```

> Web Locks API 需要安全上下文，`localhost` 满足要求。

## 技术栈与模块

| 文件 | 职责 |
| --- | --- |
| `js/backend-weblocks.js` | 主后端：`navigator.locks`，FIFO 公平性、崩溃自动释放由浏览器保证 |
| `js/backend-broadcast.js` | 降级后端：BroadcastChannel + 最小 id 协调者选举 + 心跳租约，浏览器不支持 Web Locks 时启用 |
| `js/cluster.js` | 标签页身份、消息总线、500ms 心跳 / 1.6s 租约的存活探测 |
| `js/viz.js` | Canvas 可视化：临界区持有者、FIFO 等待队列、降级执行、存活标签页 |
| `js/store.js` | IndexedDB 事件日志持久化 |
| `js/app.js` | 装配、场景演练、多锁有序获取（死锁避免） |

## 验收标准对照

- **多标签页竞争无死锁**：单锁天然无环；多锁场景统一按全局锁序（名称排序）获取，
  消除循环等待（场景⑤）。场景⑥演示无序获取造成的死锁，由超时机制兜底。
- **共享/独占语义正确**：共享锁可并发持有；独占锁与任何持有者互斥；
  降级后端严格按队首兼容性授予，共享请求不会越过排队中的独占请求（防饿死）。
- **锁超时降级**：等待超过阈值后中止请求，以"无锁保护"方式降级执行临界区，
  Canvas 中以斜纹块标示，日志记录 `timeout → degraded`。
- **等待队列公平**：Web Locks 规范保证 FIFO；降级后端协调者严格 FIFO 出队。
- **崩溃自动释放**：Web Locks 由浏览器原生保证；降级后端靠心跳租约（1.6s）检测
  崩溃并由协调者回收锁；协调者自身崩溃时由幸存最小 id 标签页接任并 resync 重建状态。
- **不支持时降级**：检测 `navigator.locks`，缺失时自动切换到 BroadcastChannel 模拟；
  也可用页面顶部开关强制降级以对比两种后端。
- **可视化实时准确**：所有标签页通过 BroadcastChannel 共享锁事件流，
  Canvas 以 rAF 渲染持有者/等待队列/降级块/存活标签页。
- **主线程不卡**：锁等待全部基于 Promise/AbortSignal，渲染在 rAF 中，无任何同步忙等。

## 手动验证建议

1. 开 3 个标签页，各自点"获取锁"，观察 Canvas 中 FIFO 队列与持有者轮换。
2. 场景②：3 个共享请求同时进入临界区；场景③：独占请求等共享全部释放后才进入。
3. 场景④：第二个请求超时后降级执行（斜纹块）。
4. 某标签页持有锁时直接关闭（或 `chrome://crash` / 任务管理器杀掉），
   约 1~2 秒内其他标签页看到锁被回收、队列前移。
5. 勾选"强制 BroadcastChannel 降级模式"刷新后重复上述步骤，行为一致。
